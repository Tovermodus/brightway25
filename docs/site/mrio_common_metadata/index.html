mrio_common_metadata

Shared metadata helpers for MRIO / EXIOBASE-style multi-region input-output datapackages — reading frictionless-data-style datapackage.json resource metadata together with bz2-compressed CSV data files, plus scripts that convert raw EXIOBASE spreadsheet downloads into that common format.

Also contains a large block of commented-out legacy/draft code — dead, not part of the current API.

Main functions & entry points

list_resources(dirpath)

__init__.py — return the resource names declared in dirpath/datapackage.json.

get_metadata_resource(dirpath, resource_name)

__init__.py — load one metadata resource's compressed CSV as a list of dicts keyed by its schema field names.

get_numeric_data_iterator(dirpath, resource_name)

__init__.py — for a numeric (row, col, value) resource with two foreignKeys, yield (row_metadata, col_metadata, float_value) tuples, resolving both foreign keys first.

convert_exiobase()

conversion/exiobase_3_hybrid_io/__init__.py and conversion/exiobase_3_hybrid_su/__init__.py — top-level conversion entry point from raw EXIOBASE spreadsheets to the common datapackage format.

Typical usage

from mrio_common_metadata import (
    list_resources,
    get_metadata_resource,
    get_numeric_data_iterator,
)

dirpath = "/path/to/exiobase-3.3.17-hybrid"

# See what's in this datapackage
print(list_resources(dirpath))
# e.g. ['locations', 'activities', 'products', 'extensions', 'IO exchanges', ...]

# Load a lookup table
locations = get_metadata_resource(dirpath, "locations")
# [{'code': 'AT', 'name': 'Austria'}, {'code': 'BE', 'name': 'Belgium'}, ...]

# Iterate over the actual IO table, with row/column metadata resolved
for row_meta, col_meta, value in get_numeric_data_iterator(dirpath, "IO exchanges"):
    if value:
        print(row_meta["name"], "->", col_meta["name"], value)

Where to look

How do I read an already-built MRIO datapackage (e.g. one bw2io uses for EXIOBASE)?

Top-level __init__.py: list_resources() to see what's available, get_metadata_resource() for lookup tables (locations, activities, products), get_numeric_data_iterator() for the actual matrix data — it resolves foreign keys via the private _get_foreign_key().
Full generated API reference →

Auto-generated from installed docstrings via pdoc (see docs/generate_api_docs.py) — every public class, function and module in mrio_common_metadata, always in sync with what is installed. Not committed to git; built fresh on every deploy.

What does a datapackage.json for this format look like?

conversion/exiobase_3_hybrid_io/datapackage.py or conversion/exiobase_3_hybrid_su/datapackage.py — the static DATAPACKAGE dict shows the full frictionless-data-style resource/schema/foreignKeys structure that the top-level reader functions expect.

How is a raw EXIOBASE .xlsb download converted into this format?

conversion/exiobase_3_hybrid_io/__init__.py's convert_exiobase(sourcedir, targetdir=None, version=...) (or the SU equivalent in conversion/exiobase_3_hybrid_su/__init__.py) is the entry point; it calls extract_metadata(), extract_extension_exchanges(), extract_production_exchanges() / extract_su_exchanges(), extract_io_exchanges(), then package_exiobase() to assemble the output using utils.write_compressed_csv().

Where are per-version source file/sheet names configured?

conversion/exiobase_3_hybrid_io/version_config.py and conversion/exiobase_3_hybrid_su/version_config.py, both a VERSIONS dict keyed by version string (e.g. "3.3.17 hybrid"), listing source spreadsheet filenames, worksheet names, and column-name → schema-field mappings.

How is the compressed CSV data itself read or written?

utils.py at the package root for the generic reader used by the runtime API (load_compressed_csv, iterate_compressed_csv, load_compressed_csv_as_dataframe); the per-variant conversion/exiobase_3_hybrid_{io,su}/utils.py for the conversion-time writer write_compressed_csv() and .xlsb extraction helpers (read_xlsb, convert_xlsb, extract_with_pandas).
Related modules:
bw2io — imports EXIOBASE/MRIO data into Brightway, consuming datapackages produced/read via this package.
bw_processing — Brightway's own datapackage format; overlapping frictionless-data-style datapackage.json metadata conventions, though a distinct on-disk layout.
