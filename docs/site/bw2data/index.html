bw2data

The core persistent data model for Brightway: projects, databases, activities/exchanges, LCIA methods and parameters — the SQLite-backed layer every other Brightway package reads or writes through.

Installed at .venv/lib/python3.11/site-packages/bw2data/, version 4.7 (PyPI bw2data>=4.4.2). Backed by SQLite via peewee. Upstream repo: brightway-lca/bw2data.

Where to look

What's the difference between a "process", a "product", and a "chimaera" node?

Verified in configuration.py (MatrixLabels) and utils.py set_correct_process_type(). There are three LCI node type values (labels.lci_node_types):

  • "process" (labels.process_node_default) — a pure process node with no product data of its own. It links to a separate "product" node via a production edge (type="production") whose input points at that other node.
  • "product" (labels.product_node_default) — a pure reference-product node: holds the product's own name/unit/categories/properties, separate from the process that makes it.
  • "processwithreferenceproduct" (labels.chimaera_node_default, informally called a chimaera node in the code and docstrings) — a single node that carries both the process data and the reference product data together. Its production exchange is self-referential: input equals the node's own (database, code) key. Every example on the Examples page that gives an activity a self-referencing production exchange (e.g. steel.new_exchange(input=steel.key, ..., type="production"), as in Examples 1 and 3) is building a chimaera-shaped node — the product's name, unit and other properties just live directly on that one node, and both the process's and the reference product's information turn up together when you look it up or search for it. Example 2 builds the same inventory both ways, side by side, and prints the resulting type of each node.

Database.write() (backends/base.py:675) auto-classifies datasets via utils.py set_correct_process_type() (utils.py:420): a dataset with an explicit self-referencing exchange, or with no explicit production edge at all (implicit self-production), is set to the chimaera type (labels.chimaera_node_default, line ~436/446). This auto-classification only runs through bulk write() — activities built one-by-one via new_activity() / .save() (as in the Examples page) keep whatever type you pass, or none, unless you set it yourself.

On the import side, bw2io.strategies.products separate_processes_from_products() does the reverse: given chimaera/process datasets, it splits each into a separate process node and a new product node (using the "reference product" field for the product's name if present), and relinks the production edge between them. See the bw2io module map.

How is an activity stored on disk?

backends/schema.py (ActivityDataset, ExchangeDataset peewee models — the SQL table schema) together with backends/proxies.py (Activity.__getitem__ / .save() for the in-memory proxy view).

How does bw2data hand off to bw2calc?

data_store.py ProcessedDataStore.process() and its override backends/base.py SQLiteBackend.process() (line ~1022) — both write a bw_processing datapackage on disk that bw2calc.LCA loads directly.

How do projects isolate data?

project.py — ProjectManager (the projects singleton, switches the active SQLite DB + data dir) and ProjectDataset; mutating methods are wrapped with the writable_project decorator.

How are LCIA methods represented?

method.py Method(ImpactAssessmentDataStore), registered in meta.py's methods singleton.

How do parameterized / formula-driven exchanges work?

parameters.py — ProjectParameter, DatabaseParameter, ActivityParameter, ParameterizedExchange, orchestrated by ParameterManager; formulas are evaluated via the separate bw2parameters package.

How do I look up a single activity, or resolve its numeric id?

utils.py get_node(**kwargs) / get_activity(key=None, **kwargs); backends/schema.py get_id(key) for the integer id used internally and by bw_processing datapackages.

What corresponds to "functional unit" and "system boundary" (goal & scope definition)?

Neither is a dedicated bw2data object. The functional unit is simply the demand dict passed to bw2calc.LCA/MultiLCA — an amount of one specific product/activity. The system boundary is implicit: whatever the technosphere graph reachable from that demand via type="technosphere" exchanges actually includes — there's no separate boundary setting to inspect. See the goal-and-scope tutorial for a worked cradle-to-gate example and the reasoning behind where the boundary is drawn.

Projects & databases on disk: how the lifecycle actually works

Verified in project.py (ProjectManager, the projects singleton created once at import time, and ProjectDataset, the peewee row backing each project). Worked examples: listing/creating/switching/ deleting projects and multiple databases in one project plus a cross-database exchange.

  • Where data lives. All project data lives under one base directory, projects._base_data_dir, resolved once when the projects singleton is constructed (ProjectManager.__init__ → _get_base_directories(), project.py:356): if the BRIGHTWAY2_DIR env var is set and points at an existing directory, that's used; otherwise it falls back to an OS-specific per-user data dir via platformdirs.PlatformDirs("Brightway3", "pylca"). Because it's resolved at import time, BRIGHTWAY2_DIR must be set before import bw2data to have any effect (see Example 4).
  • Each project's own directory is projects.dir = base_data_dir / safe_filename(project_name, full=full_hash) (_project_dir, project.py:408), where safe_filename (from bw_processing.filesystem) slugifies the name and appends an md5 hash of it — an 8-character hash by default (full_hash=False for newly created projects), or the full 32-character hash if full_hash=True. It creates five subdirectories inside on first use: backups, intermediate, lci, processed, revisions (ProjectManager._basic_directories). Logs for a project live separately, under projects.logs_dir (same base-dir-resolution logic, but for logs, and not affected by BRIGHTWAY2_DIR — see _get_base_directories).
  • Output directory for files a script writes (e.g. exports) is projects.output_dir (project.py:463): the BRIGHTWAY2_OUTPUT_DIR env var if set and valid, else preferences["output_dir"] if set and valid, else an output subdirectory auto-created under the current project's own directory.
  • Listing/creating/switching. There's no separate "create project" call — a project is created implicitly the first time projects.set_current(name) sees a name it doesn't already know (set_current → create_project, project.py:420 and :483); projects itself is iterable and yields every registered ProjectDataset, so sorted(p.name for p in projects) lists them all. The first time any project is used at all, a "default" project is auto-created (ProjectManager.__init__ calls self.set_current("default", update=False), project.py:323).
  • Deleting. projects.delete_project(name=None, delete_dir=False) (project.py:537) always unregisters the project row; only unlinks the on-disk directory too if delete_dir=True (otherwise switching back to that name later resumes with the same data — the code logs exactly this via stdout_feedback_logger.warning). It refuses to delete the last remaining project, and switches away first if you delete the currently-active one (to "default" if it still exists, else an arbitrary remaining project).
  • Copying/renaming. projects.copy_project(new_name, switch=True) (project.py:498) does a plain shutil.copytree of the whole project directory under a new hashed name, then registers a new ProjectDataset row with the same data/full_hash. rename_project(new_name) (:623) is implemented as copy-then-delete-the-old-one, and its own docstring/warning calls this "relatively expensive."
  • Housekeeping. projects.purge_deleted_directories() (project.py:581) removes any on-disk project directory that no longer has a matching registered project name (e.g. left behind by a delete_project(..., delete_dir=False) followed by manual cleanup elsewhere) — returns the number of directories removed. projects.report() (:597) walks every project, switching into each in turn, and returns (name, number of databases, total size in GB) tuples.

FAQ / troubleshooting

  • I deleted a project but the disk space didn't free up. By design: delete_project(name) defaults to delete_dir=False, so it only removes the project from the registered list — the directory (and its data) is left on disk untouched. Pass delete_dir=True explicitly to also shutil.rmtree it (see Example 4), or clean up multiple orphaned directories at once with projects.purge_deleted_directories().
  • delete_project(..., delete_dir=True) raised an AssertionError on a project that definitely exists. A real gotcha found directly in the source (project.py:557): the directory path to delete is recomputed as base_data_dir / safe_filename(victim), which uses safe_filename's default (short, 8-char hash) form — it does not look up that specific project's actual full_hash flag the way projects.dir or copy_project do. For a project stored under the full 32-character hash (created with full_hash=True, or an old project whose row predates the full_hash column and was backfilled to full_hash=1 by the add_full_hash_column migration in this same file), the recomputed path won't match the real directory, and the following assert dir_path.is_dir() fails. Workaround: delete the directory yourself (it's projects.dir while that project is current) instead of relying on delete_dir=True, or convert the project to the short-hash form first with projects.use_short_hash() (project.py:639).
  • My project's directory name has garbled/missing characters for a non-ASCII project name. Verified by calling bw_processing.safe_filename directly: it runs the name through Unicode NFKD normalization and then strips anything that isn't a "word" character before appending the hash. For an accented name like "café project" this cleanly folds to "cafe-project.<hash>". But for scripts that use combining diacritics/marks — e.g. Japanese dakuten-marked katakana — NFKD decomposition splits the base character from its mark, and the mark then gets silently stripped as "not a word character," changing the visible characters (a voiced プ "pu" can come out as its unvoiced base フ "fu" in the directory name). This is a purely cosmetic/readability issue, not a data-loss or collision one — the appended md5 hash suffix is computed from the original, un-mangled name, so two differently named projects that fold to the same slug still get distinct, non-colliding directories; only the human-readable prefix of the directory name is affected.
