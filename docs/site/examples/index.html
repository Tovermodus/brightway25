1. Create a database, add an activity, look it up

Registers a new database, creates a node with a production exchange (nothing persists until .save()), then looks it up again with get_node. For loading many activities at once instead of one-by-one, see Database.write() in the bw2data module map.

Code

import bw2data as bd

bd.projects.set_current("my-project")   # isolated project: SQLite DB + data dir

db = bd.Database("example_db")
db.register()                            # required before writing; database now exists, empty

steel = db.new_activity(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()                              # nothing persists until .save() is called
steel.new_exchange(input=steel.key, amount=1, type="production").save()

print(len(db))
activity = bd.get_node(database="example_db", name="steel production")
for exc in activity.exchanges():
    print(exc.input, exc.amount, exc["type"])

Output

1
'steel production' (kilogram, GLO, None) 1 production

2. Chimaera vs. non-chimaera nodes

Same steel production inventory, built two ways, to show the difference between a chimaera node and separate process/product nodes. Database.write() auto-classifies each: a self-referencing production exchange (input equal to the node's own key) becomes "processwithreferenceproduct" — a single node holding both the process and its reference product. A production exchange pointing at a different node stays a plain "process", with the product's own data living on a separate "product" node.

Code

import bw2data as bd

bd.projects.set_current("my-project")
db = bd.Database("example_db")
db.register()

db.write({
    # Chimaera: one node IS both the process and its reference product.
    # A self-referencing production exchange (input == this node's own key)
    # makes Database.write() auto-classify it as "processwithreferenceproduct".
    ("example_db", "steel-chimaera"): {
        "name": "steel production",
        "unit": "kilogram",
        "exchanges": [
            {"input": ("example_db", "steel-chimaera"), "amount": 1, "type": "production"},
        ],
    },
    # Non-chimaera: process and product are two separate nodes. The
    # process's production exchange points *away* from itself, at the
    # product node — so it's auto-classified as a plain "process".
    ("example_db", "steel-process"): {
        "name": "steel production",
        "unit": "kilogram",
        "type": "process",
        "exchanges": [
            {"input": ("example_db", "steel-product"), "amount": 1, "type": "production"},
        ],
    },
    ("example_db", "steel-product"): {
        "name": "steel",
        "unit": "kilogram",
        "type": "product",
    },
})

for code in ("steel-chimaera", "steel-process", "steel-product"):
    act = bd.get_node(database="example_db", code=code)
    print(f"{code:16s} type={act['type']:28s} name={act['name']!r}")

Output

steel-chimaera   type=processwithreferenceproduct  name='steel production'
steel-process    type=process                      name='steel production'
steel-product    type=product                      name='steel'

Pick chimaera for simple one-node-per-flow databases (least bookkeeping); pick separate process/product nodes when the reference product needs its own identity — shared by multiple processes, or allocated across co-products via multifunctional. bw2io's strategies.products.separate_processes_from_products() converts chimaera-shaped imports into the separate-node form; see bw2io's note on this.

3. Run a full LCA: biosphere flow + method + bw2calc

Ties bw2data together with bw2calc — a minimal but complete inventory + impact calculation: a process emits CO₂, a Method characterizes it, bw2calc.LCA solves the score.

Code

import bw2data as bd
import bw2calc as bc

bd.projects.set_current("my-project")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

db = bd.Database("example_db")
db.register()
steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()
steel.new_exchange(input=co2.key, amount=1.8, type="biosphere").save()   # 1.8 kg CO2 per kg steel

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])            # characterization factor: 1 kg CO2 = 1 kg CO2-eq

lca = bc.LCA({steel.key: 1}, method_key)  # score for producing 1 kg of steel
lca.lci()
lca.lcia()
print(lca.score)

Output

1.7999999523162842

4. List/create/switch/delete projects, and see where data lives on disk

Every Brightway project is an isolated SQLite database plus a data directory under bw2data.projects.dir. The base directory for all projects defaults to an OS-specific per-user data dir (via platformdirs), but the BRIGHTWAY2_DIR environment variable overrides it — set it before importing bw2data, since the base directory is resolved once, at import time, by the projects singleton. A project is created the first time projects.set_current(name) sees a name it doesn't recognize; there's no separate "create" call. Each project's on-disk directory name is <name>.<8-char md5 hash of name> (the hash avoids filesystem-unsafe-name and collision problems) — see ProjectManager._project_dir in project.py.

Code

import os
import tempfile
from pathlib import Path

tmp = tempfile.mkdtemp(prefix="bw25-example-")
os.environ["BRIGHTWAY2_DIR"] = tmp          # override where all project data lives on disk

import bw2data as bd

print(sorted(p.name for p in bd.projects))    # 'default' always exists

bd.projects.set_current("demo-project")       # created automatically on first use
bd.Database("demo_db").register()

print(sorted(p.name for p in bd.projects))
print(bd.projects.current)
print(bd.projects.dir.parent == Path(tmp))    # each project is a subdir of BRIGHTWAY2_DIR
print(bd.projects.dir.name)                   # "<name>.<8-char hash>" -- avoids filename collisions

bd.projects.set_current("default")            # can't delete the *current* project
print(bd.projects.delete_project("demo-project", delete_dir=True))  # also removes the directory
print(sorted(p.name for p in bd.projects))

Output

['default']
['default', 'demo-project']
demo-project
True
demo-project.5ec5629b
default
['default']

By default delete_project(name) only unregisters the project name — the data directory is left on disk, so switching back to that name later resumes with the same data. Pass delete_dir=True (as above) to also shutil.rmtree the directory. Note one real gotcha found in project.py: delete_project recomputes the directory to delete as safe_filename(name) with the default (short, 8-char) hash, regardless of the project's actual full_hash setting — for a project created with full_hash=True (or migrated from an old Brightway version, where existing rows were backfilled with full_hash=1 by add_full_hash_column), that computed path won't match the real directory and the delete's internal assert dir_path.is_dir() raises. If you hit that, delete the project's directory yourself (it's projects.dir while that project is current) rather than relying on delete_dir=True.

5. Multiple databases in one project, and a cross-database exchange

A project can hold any number of databases; each is just a named partition of rows in the same project SQLite file (bd.databases lists every registered name). Nothing stops an exchange's input from pointing at a node in a different database within the same project -- that's how real supply chains span, e.g., a "biosphere" flows database and several technosphere databases.

Code

import bw2data as bd

bd.projects.set_current("my-project")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

steel_db = bd.Database("steel_supply_chain")
steel_db.register()
ore = steel_db.new_node(code="ore", name="iron ore mining", unit="kilogram", location="GLO")
ore.save()
ore.new_exchange(input=ore.key, amount=1, type="production").save()
ore.new_exchange(input=co2.key, amount=0.05, type="biosphere").save()

parts_db = bd.Database("parts_supply_chain")
parts_db.register()
part = parts_db.new_node(code="part", name="steel part", unit="unit", location="GLO")
part.save()
part.new_exchange(input=part.key, amount=1, type="production").save()
# cross-database technosphere exchange: parts_supply_chain consumes from steel_supply_chain
part.new_exchange(input=ore.key, amount=2, type="technosphere").save()

print(sorted(bd.databases))                     # every registered database in this project
print(len(steel_db), len(parts_db))              # each Database is scoped to its own rows

for exc in part.exchanges():
    print(exc["type"], exc.input, "in", exc.input["database"])

Output

['biosphere', 'parts_supply_chain', 'steel_supply_chain']
1 1
production 'steel part' (unit, GLO, None) in parts_supply_chain
technosphere 'iron ore mining' (kilogram, GLO, None) in steel_supply_chain

See also: the bw2calc module map. Builds on example 3 above (a single method, single functional unit) to show the two other calculation shapes bw2calc.MultiLCA and stochastic use_distributions=True LCA cover.

6. Multiple impact categories × multiple functional units in one go: MultiLCA

The single-LCA class from example 3 answers "what is the score of demand X under method Y?" one pair at a time. bw2calc.MultiLCA instead builds one shared technosphere/biosphere matrix and solves every (functional unit, impact category) combination against it, driven by a MethodConfig-shaped dict. bd.get_multilca_data_objs() (bw2data/compat.py) collects the datapackages for all of it.

Code

import bw2data as bd
import bw2calc as bc

bd.projects.set_current("my-project")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()
so2 = biosphere.new_node(code="so2", name="sulfur dioxide", unit="kilogram", type="emission")
so2.save()

db = bd.Database("example_db")
db.register()
steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()
steel.new_exchange(input=co2.key, amount=1.8, type="biosphere").save()
steel.new_exchange(input=so2.key, amount=0.02, type="biosphere").save()

concrete = db.new_node(code="concrete", name="concrete production", unit="kilogram", location="GLO")
concrete.save()
concrete.new_exchange(input=concrete.key, amount=1, type="production").save()
concrete.new_exchange(input=co2.key, amount=0.1, type="biosphere").save()

gwp_key = ("tutorial_method", "gwp")
gwp = bd.Method(gwp_key)
gwp.register(unit="kg CO2-eq")
gwp.write([(co2.key, 1.0)])

acid_key = ("tutorial_method", "acidification")
acid = bd.Method(acid_key)
acid.register(unit="kg SO2-eq")
acid.write([(so2.key, 1.0)])

# MultiLCA runs many (functional unit x impact category) combinations
# together, sharing one factorized technosphere solve.
func_units = {"1kg steel": {steel.id: 1}, "1kg concrete": {concrete.id: 1}}
method_config = {"impact_categories": [gwp_key, acid_key]}
data_objs = bd.get_multilca_data_objs(func_units, method_config)

mlca = bc.MultiLCA(demands=func_units, method_config=method_config, data_objs=data_objs)
mlca.lci()
mlca.lcia()

for (ic, fu), score in sorted(mlca.scores.items()):
    print(f"{fu:12s} {ic} = {score}")

Output

1kg concrete ('tutorial_method', 'acidification') = 0.0
1kg steel    ('tutorial_method', 'acidification') = 0.019999999552965164
1kg concrete ('tutorial_method', 'gwp') = 0.10000000149011612
1kg steel    ('tutorial_method', 'gwp') = 1.7999999523162842

mlca.scores keys are (impact_category, functional_unit_name) tuples — the impact category tuple registered in method_config["impact_categories"], and whatever string key the functional unit was given in demands. Functional unit dicts must use integer node ids (steel.id), not (database, code) keys or Node objects, unlike plain LCA.

7. Stochastic (Monte Carlo) LCA with use_distributions=True

An exchange's uncertainty is stored as extra fields on the exchange ("uncertainty type", "loc", "scale", ...) using the same integer ids as stats_arrays' UncertaintyType (normal = 3). Passing use_distributions=True to bw2calc.LCA makes every next(lca) call re-sample each uncertain value from its distribution and resolve a fresh score; seed_override seeds that sampling for reproducibility.

Code

import numpy as np
import bw2data as bd
import bw2calc as bc

bd.projects.set_current("my-project")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

db = bd.Database("example_db")
db.register()
steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()

# Uncertain CO2 factor: normal distribution, mean 1.8 kg, std 0.2 kg.
# Field names/values follow stats_arrays' UncertaintyType (normal id == 3);
# bw2data stores them on the exchange as "uncertainty type"/"loc"/"scale".
co2_exchange = steel.new_exchange(input=co2.key, amount=1.8, type="biosphere")
co2_exchange["uncertainty type"] = 3  # stats_arrays.UncertaintyType.normal
co2_exchange["loc"] = 1.8
co2_exchange["scale"] = 0.2
co2_exchange.save()

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])

# use_distributions=True samples a fresh value per exchange's distribution
# on every iteration; seed_override makes that sampling reproducible.
lca = bc.LCA({steel.key: 1}, method_key, use_distributions=True, seed_override=42)
lca.lci()
lca.lcia()

scores = [lca.score]
for _ in range(999):
    next(lca)                 # re-samples the technosphere/biosphere/CF matrices
    scores.append(lca.score)

scores = np.array(scores)
print(f"iterations = {len(scores)}")
print(f"mean       = {scores.mean():.4f}")
print(f"std        = {scores.std():.4f}")
print(f"min        = {scores.min():.4f}")
print(f"max        = {scores.max():.4f}")

Output

iterations = 1000
mean       = 1.8039
std        = 0.1957
min        = 1.1517
max        = 2.5705

This is the same mechanism PartitionedMonteCarloLCA (bw2calc module map) builds on for large background systems — sample once, re-solve, repeat. The RNG dispatch for mixed uncertainty types on the underlying params array is stats_arrays.MCRandomNumberGenerator; see the stats_arrays module map.

8. Import an LCI sheet with ExcelImporter, then check what linked

Runs ExcelImporter against bw2io.get_xlsx_example_filepath() — the small workbook bw2io ships for its own tests, describing 3 US LCI processes. A hand-registered biosphere3 database (normally created once per project by bw2io.bw2setup()) lets the 5 biosphere flows in the sheet link automatically via link_iterable_by_fields; .statistics() then reports what's still unlinked — here, the two processes' own self-referencing production exchanges and one technosphere input, because this fixture deliberately doesn't give every activity a matching reference product. Checking .statistics() / exc.get("input") before .write_database() is the normal way to catch this before it silently drops data.

Code

import contextlib
import io

import bw2data as bd
import bw2io as bi

bd.projects.set_current("excel-import-demo")

# A real project gets this from bw2io.bw2setup() / create_default_biosphere3();
# here we register just the 5 flows the example sheet references, by hand.
biosphere = bd.Database("biosphere3")
biosphere.write({
    ("biosphere3", "ammonia"): {
        "name": "Ammonia", "unit": "kilogram", "type": "emission",
        "categories": ("air", "urban air close to ground"),
    },
    ("biosphere3", "methanol-air"): {
        "name": "Methanol", "unit": "kilogram", "type": "emission",
        "categories": ("air",),
    },
    ("biosphere3", "bod5"): {
        "name": "BOD5, Biological Oxygen Demand", "unit": "kilogram", "type": "emission",
        "categories": ("water", "surface water"),
    },
    ("biosphere3", "co2-fossil"): {
        "name": "Carbon dioxide, fossil", "unit": "kilogram", "type": "emission",
        "categories": ("air",),
    },
    ("biosphere3", "suspended-solids"): {
        "name": "Suspended solids, unspecified", "unit": "kilogram", "type": "emission",
        "categories": ("water",),
    },
})

# ExcelImporter.__init__ and apply_strategies() print an elapsed-time float
# that isn't byte-for-byte reproducible across runs -- swallow that, keep
# the deterministic statistics() summary below.
with contextlib.redirect_stdout(io.StringIO()):
    imp = bi.ExcelImporter(bi.get_xlsx_example_filepath())
    imp.apply_strategies(verbose=False)

imp.statistics()

acetic_acid = next(ds for ds in imp.data if ds["name"] == "Acetic acid, at plant")
for exc in acetic_acid["exchanges"]:
    print(exc["type"], repr(exc["name"]), "->", "linked" if exc.get("input") else "UNLINKED")

9. Round-trip a database through a BW2Package archive

BW2Package is the format-agnostic archive bw2io uses for backups and for remote.install_project() — a bzip2 JSON file that round-trips any bw2data DataStore (database, method, ...). export_obj() writes it; import_file() reads it back and re-registers/writes the object, here into a completely different project, showing the archive carries everything needed to recreate the database elsewhere.

Code

import bw2data as bd
import bw2io as bi

bd.projects.set_current("bw2package-roundtrip-demo")

db = bd.Database("example_db")
db.write({
    ("example_db", "steel"): {
        "name": "steel production", "unit": "kilogram", "location": "GLO",
        "exchanges": [
            {"input": ("example_db", "steel"), "amount": 1, "type": "production"},
        ],
    },
})

path = bi.BW2Package.export_obj(db, filename="steel-archive")
print("archive filename:", path.split("/")[-1])

bd.projects.set_current("bw2package-roundtrip-target")
restored = bi.BW2Package.import_file(path)[0]
print(type(restored).__name__, restored.name, len(restored))
activity = bd.get_node(database="example_db", code="steel")
print(activity["name"], activity["unit"], activity["location"])

10. Apply a migration to rename and rescale an exchange

A Migration is a named, versioned old-value→new-value lookup table stored per-project (the same mechanism behind the built-in biosphere-2-3-names / simapro-ecoinvent-* migrations that create_core_migrations() registers); the migrate_exchanges strategy applies one to raw import data. Here a migration both renames a stale flow label and — via the special "multiplier" key, applied by utils.rescale_exchange — converts its unit and amount from Wh to kWh. This is the same mechanism bw_migrations and randonneur-sourced data feed into during a real ecoinvent/SimaPro import.

Code

import bw2data as bd
import bw2io as bi
from bw2io.strategies import migrate_exchanges

bd.projects.set_current("migration-demo")

migration = bi.Migration("fix-old-electricity-unit")
migration.write(
    {
        "fields": ["name", "unit"],
        "data": [
            (
                ["electricity, old label", "Wh"],
                {"name": "electricity", "unit": "kilowatt hour", "multiplier": 0.001},
            ),
        ],
    },
    description="Rename a stale flow label and convert Wh -> kWh",
)

data = [
    {
        "name": "widget production",
        "database": "example_db",
        "code": "widget",
        "exchanges": [
            {
                "name": "electricity, old label",
                "unit": "Wh",
                "amount": 500,
                "type": "technosphere",
            },
        ],
    }
]

fixed = migrate_exchanges(data, migration="fix-old-electricity-unit")
exc = fixed[0]["exchanges"][0]
print(exc["name"], exc["unit"], exc["amount"])
