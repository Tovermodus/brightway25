Tutorial: run your first LCA calculation

Build a tiny inventory from scratch with bw2data, then solve it with bw2calc.LCA — walking through .lci() and .lcia() separately so you can see what each one actually builds.

Everything here uses the real installed bw2data/bw2calc API (.venv/lib/python3.11/site-packages/), verified by running it. See the bw2data module map and the bw2calc module map for the full picture of how these layers fit together. If you haven't built a database before, the empty-database tutorial covers that groundwork in more depth.

1. Set up a project and a biosphere database

An LCA needs at least two databases: a biosphere database holding elementary flows (emissions, resource extractions — things exchanged with the environment, not produced by any process) and a foreground database holding the processes you actually want to model. Start with the biosphere side: one flow, carbon dioxide. 

import bw2data as bd

bd.projects.set_current("first-lca-tutorial")

biosphere = bd.Database("biosphere")
biosphere.register()

co2 = biosphere.new_node(code="co2", name="Carbon dioxide", unit="kilogram", type="emission")
co2.save()

This is the same new_node/.save() pattern as any other activity (see the empty-database tutorial) — a biosphere flow is just a node with type="emission" instead of "process" (bw2data/configuration.py labels.biosphere_node_default is "emission"). It doesn't need a production exchange; nothing "produces" CO2 as a technosphere output — processes only emit it via a biosphere-type exchange, step 2.

2. Build the foreground process

Now add one process activity — electricity production — with a production exchange (so bw2calc knows what 1 unit of this activity supplies) and a biosphere exchange linking it to the CO2 flow (so running it has an environmental consequence): 

foreground = bd.Database("foreground")
foreground.register()

electricity = foreground.new_node(
    code="electricity",
    name="electricity production",
    unit="kilowatt hour",
    location="GLO",
    type="process",
)
electricity.save()

electricity.new_exchange(input=electricity.key, amount=1, type="production").save()
electricity.new_exchange(input=co2.key, amount=0.5, type="biosphere").save()

Read the second exchange as: producing 1 kWh of electricity emits 0.5 kg of CO2. That's the entire inventory — one biosphere flow, one process, one edge between them — deliberately minimal so every number in the final score is traceable by hand.

3. Define an LCIA method with a characterization factor

An LCIA method (bw2data/method.py Method, an ImpactAssessmentDataStore) is a set of characterization factors: a weight applied to each biosphere flow it cares about. Register one and give it a single factor of 1.0 for CO2 — so this toy method's score is directly the kilograms of CO2 emitted, keeping the arithmetic transparent: 

method_key = ("tutorial", "climate change")
method = bd.Method(method_key)
method.register()
method.write([(co2.key, 1.0)])

Method.write() takes a list of (flow_key, factor) tuples (a third, uncertainty-dict element is optional per row) and persists them, the same way SQLiteBackend.write() persists activity data. A method must be registered before it can be characterized against.

4. Construct the LCA object

bw2calc.LCA(demand, method=...) (bw2calc/lca.py LCA.__init__, line ~43) takes a functional unit — a dict mapping an activity (or its key, or its integer id) to a demanded amount — plus the method tuple. Ask for 10 kWh of our electricity: 

import bw2calc as bc

lca = bc.LCA({electricity: 10}, method=method_key)

Under the hood, __init__ calls bw2data.prepare_lca_inputs(demand=..., method=...) (lca.py line ~117) to resolve the demand and gather the bw_processing datapackages for the technosphere, biosphere, and characterization matrices — but nothing is loaded into actual matrices yet. Confirm that: right after construction, the object has no technosphere_matrix attribute at all. 

print(hasattr(lca, "technosphere_matrix"))  # False — nothing built yet

5. Run .lci() — the inventory

LCA.lci() (defined on LCABase in lca_base.py, line ~157) does three things, per its own docstring: load the LCI data and build the technosphere/biosphere matrices (load_lci_data()), build the demand array from your functional unit (build_demand_array()), then solve the linear system A·s = f for the supply array s and compute the inventory as B · diag(s) (lca.py lci_calculation(), line ~290-302, via solve_linear_system() in lca_base.py line ~131, using scipy.sparse.linalg.spsolve or a factorized solver if one was installed at import time): 

lca.lci()

print(lca.supply_array)          # how much of each technosphere activity must run
print(lca.inventory.sum())       # total (characterization-independent) biosphere flow, weighted by supply

After .lci(), lca.technosphere_matrix, lca.biosphere_matrix, lca.supply_array, and lca.inventory all exist — but lca.characterized_inventory and lca.score do not yet. .lci() never touches the characterization matrix at all; it only knows about the technosphere and biosphere.

6. Run .lcia() — the impact assessment

LCA.lcia() (lca_base.py line ~193) loads and builds the characterization matrix, then multiplies it by the inventory computed in step 5 (lca.py lcia_calculation(), line ~304-311: self.characterized_inventory = self.characterization_matrix @ self.inventory). It requires .lci() to have already run — it reuses self.inventory rather than recomputing it: 

lca.lcia()

print(lca.characterized_inventory.sum())

7. Read the score

lca.score is a property (lca.py line ~332) that sums characterized_inventory (or the normalized/weighted inventory instead, if you called .normalize()/.weight() — not used here). It asserts characterized_inventory exists rather than raising a plain AttributeError — so accessing .score before .lcia() fails with AssertionError: Must do LCIA first, not a missing-attribute error: 

print(lca.score)
5.0

10 kWh × 0.5 kg CO2/kWh × a characterization factor of 1.0 = 5.0 — every step of that arithmetic is visible in supply_array, inventory, and characterized_inventory above.

Under the hood: the A/B/C formulation

This whole tutorial is one instance of Brightway's standard matrix formulation. A is the technosphere matrix (here 1×1: just "electricity production" supplying itself), B is the biosphere matrix (1×1: the CO2 exchange), and C is the characterization matrix (1×1: the factor of 1.0). Given a demand vector f (here [10]), the LCA score is: 

score = C · B · A⁻¹ · f

.lci() computes A⁻¹·f (as the supply array s, without ever forming the inverse — it solves A·s = f directly) and then B·s (the inventory); .lcia() applies C on top. Print the shapes to see it directly — all three matrices come out 1×1 here because this inventory has exactly one process, one biosphere flow, and one characterized flow: 

print(lca.technosphere_matrix.shape)       # (1, 1)
print(lca.biosphere_matrix.shape)          # (1, 1)
print(lca.characterization_matrix.shape)   # (1, 1)

Full example, start to finish

import bw2data as bd
import bw2calc as bc

bd.projects.set_current("first-lca-tutorial")

# 1. Biosphere database: one emission flow
biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="Carbon dioxide", unit="kilogram", type="emission")
co2.save()

# 2. Foreground database: one process, with a production exchange and a biosphere exchange
foreground = bd.Database("foreground")
foreground.register()
electricity = foreground.new_node(
    code="electricity",
    name="electricity production",
    unit="kilowatt hour",
    location="GLO",
    type="process",
)
electricity.save()
electricity.new_exchange(input=electricity.key, amount=1, type="production").save()
electricity.new_exchange(input=co2.key, amount=0.5, type="biosphere").save()

# 3. Method: one characterization factor for CO2
method_key = ("tutorial", "climate change")
method = bd.Method(method_key)
method.register()
method.write([(co2.key, 1.0)])

# 4. LCA: 10 kWh of electricity
lca = bc.LCA({electricity: 10}, method=method_key)

lca.lci()
print("supply_array:", lca.supply_array)
print("inventory (biosphere flows for this supply):", lca.inventory.sum())

lca.lcia()
print("score:", lca.score)
supply_array: [10.]
inventory (biosphere flows for this supply): 5.0
score: 5.0

Notes & gotchas

  • .lci() and .lcia() are independent steps, not one call. This matters in practice: you can call .lci() once and then .lcia() with several different methods against the same solved inventory (lcia(demand=...) even lets you re-run against a different demand without rebuilding the technosphere matrix), or use bc.MultiLCA to share one factorized technosphere across many functional units and methods at once (see modules/bw2calc/CLAUDE.md).
  • lca.score raises AssertionError, not AttributeError, if you skip .lcia(). Verified directly: hasattr(lca, "score") before calling .lcia() does not return False — it propagates the assertion, because hasattr in Python 3 only swallows AttributeError (bw2calc/lca.py line ~340).
  • Elementary flows are just nodes with type="emission". There's no separate "biosphere flow" class — a biosphere database is a regular bw2data.Database, and what makes an exchange a biosphere exchange is type="biosphere" on the exchange that references it, not anything special about the flow node itself.
  • The production exchange is what makes the technosphere matrix square. Without electricity.new_exchange(input=electricity.key, amount=1, type="production"), the process has no column entry in A for its own output, and bw2calc raises (see bw2calc/errors.py NonsquareTechnosphere).
  • Everything here is minimal on purpose. A realistic inventory has many processes, many biosphere flows, and technosphere-to-technosphere exchanges between processes — see the bw2data Examples section for a slightly larger round trip, and the empty-database tutorial for building up a multi-activity database step by step.
