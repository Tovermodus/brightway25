Tutorial: allocate a multifunctional process

How to build a process with more than one functional co-product, let multifunctional split it into single-output processes, and see why the allocation strategy you pick changes the LCA score each co-product gets.

Everything here uses the real installed multifunctional API (.venv/lib/python3.11/site-packages/multifunctional/), verified by running it. See the multifunctional module map for the full picture of what else it can do, the bw2data module map for how databases/activities/exchanges work underneath it, and the bw2calc module map for how the final LCA call in this tutorial works.

1. What a multifunctional process is, and why plain LCA chokes on it

A normal bw2data process has exactly one type="production" exchange — one thing it makes, in some amount. Stack up enough of those processes and you get a square technosphere matrix: as many processes as there are products, which bw2calc.LCA can invert to solve for the demand you asked for.

A multifunctional process breaks that assumption: it has more than one functional (reference) exchange — think a refinery that turns one input of crude oil into both diesel and petroleum coke in the same operation. You can't ask "what's the impact of 1 kg of diesel?" from a process like that without first deciding how much of the refinery's shared burden (the crude oil, the energy, the CO₂) belongs to the diesel versus the coke. Until that's decided, the matrix isn't square and bw2calc has nothing to solve.

The multifunctional package (see its module map, "Purpose" section) resolves this per process via one of three approaches — a database was hand-built to already be square (skip_allocation), one output is credited against another process's output (substitution), or, the case this tutorial covers, the process is allocated: split into several read-only, single-output processes, one per functional product, using a pluggable strategy such as economic price, mass, or an equal split.

2. Build a two-product refinery process

A database created with backend="multifunctional" is a MultifunctionalDatabase — a drop-in subclass of the normal SQLite backend that knows how to handle multiple functional exchanges. The scenario below: a "crude oil distillation" process with two functional (reference) production exchanges — diesel (100 kg) and petroleum coke (25 kg) — plus one non-functional biosphere exchange (40 kg CO₂) that has to be split between them. Each functional exchange carries a properties dict with both a price (€/kg) and a mass value, so the same process can be re-allocated by either property later in the tutorial. 

import bw2data as bd
import multifunctional  # noqa: F401  -- registers the "multifunctional" backend into bw2data

bd.projects.set_current("mf-tutorial")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

db = bd.Database("refinery_db", backend="multifunctional")
db.register(default_allocation="price")

db.write({
    ("refinery_db", "crude_distillation"): {
        "name": "crude oil distillation",
        "location": "GLO",
        "exchanges": [
            {
                "functional": True, "type": "production",
                "name": "diesel", "unit": "kilogram", "amount": 100,
                "properties": {"price": 1.1, "mass": 100},
            },
            {
                "functional": True, "type": "production",
                "name": "petroleum coke", "unit": "kilogram", "amount": 25,
                "properties": {"price": 0.2, "mass": 25},
            },
            {
                "input": co2.key, "type": "biosphere", "amount": 40,
            },
        ],
    },
})

Two things worth calling out before moving on:

  • db.register(default_allocation="price") sets the strategy before the first write(). MultifunctionalDatabase.process() runs allocation unconditionally whenever the database is processed, so if no strategy can be resolved — not on the node, not on the database — write() raises ValueError: Can't find `default_allocation` in input arguments, or process/database metadata. (verified by dropping default_allocation from register() above and re-running). Set it up front; there's no useful default to fall back on.
  • The biosphere exchange has no "functional": True and no "input" pointing at a not-yet-existing product — it links straight to the already-registered co2 flow node. The two diesel/petroleum coke exchanges, by contrast, deliberately have no "input" key at all: multifunctional generates fresh product nodes for functional exchanges as part of allocation. Supplying an explicit "input" yourself only works if it already points at an existing product node — otherwise UnknownObject blows up later when the datapackage is built, since generic_allocation() strips a same-key placeholder back off before generating the real one. Easiest fix: just leave functional exchanges without an "input" and let allocation create it.

3. Writing the database already ran allocation

There's no separate "now allocate" step to remember — MultifunctionalDatabase.write() labels multifunctional nodes and .process() (called at the end of write()) runs node.allocate() on every node with more than one functional exchange, using whatever strategy register(default_allocation=...) set. Inspecting what came out: 

proc = bd.get_node(database="refinery_db", code="crude_distillation")
print("multifunctional:", proc.multifunctional)
print("type:", proc["type"])

for exc in sorted((e for e in proc.exchanges() if e.get("functional")), key=lambda e: e["name"]):
    print(f"  {exc['name']:16s} amount={exc.amount:6} price={exc['properties']['price']:5} "
          f"allocation_factor={exc['mf_allocation_factor']:.4f}")

for act in sorted((a for a in db if a.get("type") == "readonly_process"), key=lambda a: a["reference product"]):
    print(f"  readonly process, reference product={act['reference product']:16s} "
          f"production amount={act['production amount']}")

  readonly process, reference product=petroleum coke   production amount=25

Two kinds of node now exist side by side in refinery_db: the original crude_distillation node, still type="multifunctional" and still holding both functional exchanges (now annotated with an mf_allocation_factor each — economic price share, normalized to sum to 1 across the process's functional edges), and two new, generated readonly_process nodes, one per product, each carrying its own share of the production amount. The multifunctional parent is still there and still editable; the read-only children are what bw2calc.LCA can actually run on, which is the point of section 5.

4. Same process, different allocation strategy, different split

diesel is by far the heavier product by mass (100 kg vs. 25 kg) but also the pricier one per kilogram (€1.10 vs. €0.20) — mass and price roughly agree here, but not exactly, which is enough to show the strategies diverging. node.allocate(strategy) re-runs allocation on demand with a different strategy label, pulled from multifunctional.allocation_strategies ("price" and "mass" are property allocation normalized by production amount; "equal" just gives every functional exchange a factor of 1.0, i.e. splits by production amount only): 

for strategy in ("price", "mass", "equal"):
    proc.allocate(strategy)
    factors = {e["name"]: e["mf_allocation_factor"] for e in proc.exchanges() if e.get("functional")}
    print(f"strategy={strategy:6s} diesel={factors['diesel']:.4f}  petroleum coke={factors['petroleum coke']:.4f}")
strategy=price  diesel=0.9565  petroleum coke=0.0435
strategy=mass   diesel=0.9412  petroleum coke=0.0588
strategy=equal  diesel=0.5000  petroleum coke=0.5000

Under "price" diesel absorbs 95.65% of the shared burden (it's worth more per kilogram, on top of being the bulk of the mass); under "mass" that drops slightly to 94.12% since mass allocation ignores the price gap entirely; under "equal" it drops all the way to 50% because "equal" ignores both mass and price and gives each product — not each kilogram — the same weight. Every call to .allocate() also regenerates the readonly_process nodes behind the scenes (update_datasets_from_allocation_results in multifunctional/utils.py, stamped with a fresh mf_allocation_run_uuid; stale ones from the previous run get purged), so the read-only nodes fetched in the next section always reflect whichever strategy ran most recently. This tutorial continues with "price": 

proc.allocate("price")

5. Run a normal, square-matrix LCA on one co-product

This is the payoff: diesel_proc below is an ordinary ReadOnlyProcessWithReferenceProduct — a single-output process like any other, with a production exchange back to itself and its price-allocated share (95.65%) of the parent's CO₂ exchange. bw2calc.LCA doesn't need to know anything about multifunctional processes at all here; it just sees a square system. 

import bw2calc as bc

diesel_proc = bd.get_node(database="refinery_db", **{"reference product": "diesel"})
coke_proc = bd.get_node(database="refinery_db", **{"reference product": "petroleum coke"})

print("diesel exchanges:")
for exc in diesel_proc.exchanges():
    print(f"  {exc.input['name']:20s} type={exc['type']:12s} amount={exc.amount}")

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])

lca = bc.LCA({diesel_proc.key: 1}, method_key)
lca.lci()
lca.lcia()
print("LCA score, 1 kg diesel (price allocation):", round(lca.score, 4))

lca2 = bc.LCA({coke_proc.key: 1}, method_key)
lca2.lci()
lca2.lcia()
print("LCA score, 1 kg petroleum coke (price allocation):", round(lca2.score, 4))

  crude oil distillation type=production   amount=100

LCA score, 1 kg diesel (price allocation): 0.3826
LCA score, 1 kg petroleum coke (price allocation): 0.0696

Sanity check: the diesel process carries 38.26 of the parent's 40 kg CO₂ (95.65%, matching the allocation factor from section 3), scaled down per kilogram of production (100 kg) to a score of 0.3826 per kg. Multiplying each score back up by its production amount and summing — 0.3826 × 100 + 0.0696 × 25 = 40.0 — reproduces the original process's total 40 kg CO₂ exactly, confirming the split accounts for the whole shared burden rather than double-counting or dropping any of it.

Notes & gotchas

  • default_allocation must be set before the first write(). MultifunctionalDatabase.process() (called at the end of every write()) runs allocation unconditionally on any node with more than one functional exchange. If no strategy is set — not passed to register(), not set as a node's own default_allocation — that first write() raises ValueError: Can't find `default_allocation` in input arguments, or process/database metadata. There's no silent fallback strategy, so decide up front.
  • Don't hand-supply "input" on a functional exchange unless it already points at an existing product node. Leave it out and let allocation generate the product node for you — a placeholder/incorrect "input" either gets stripped and regenerated (if it happens to match the exchange's own key, treated as a same-key artifact) or, if it points at something that doesn't exist yet, raises UnknownObject once the datapackage is built. See the module map's notes on add_exchange_input_if_missing / generic_allocation.
  • Read-only processes really are read-only. ReadOnlyProcessWithReferenceProduct's __setitem__, copy(), and new_edge() all raise NotImplementedError, and its exchanges are ReadOnlyExchange/ReadOnlyExchanges proxies that block save()/delete()/__setitem__ too. To change anything, edit the multifunctional parent (reachable via the read-only node's .parent property) and re-run .allocate() — don't try to edit the generated child directly.
  • Re-allocating regenerates the read-only nodes, keyed by run UUID. Every .allocate() call stamps a fresh mf_allocation_run_uuid on the parent; on the next save(), purge_expired_linked_readonly_processes deletes any readonly_process node whose mf_parent_key matches the parent but whose UUID is stale. In practice this means fetching a co-product by {"reference product": "diesel"} (as this tutorial does) always gets you the node from the most recent allocation run, not a particular historical one — if you need to compare strategies side by side rather than sequentially, read off the factors right after each .allocate() call instead, as section 4 does.
