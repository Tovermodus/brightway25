Tutorial: allocate a multifunctional (co-product) process

Build a process with two functional co-products on one multifunctional-backend bw2data database, give each co-product a numeric allocation property, split the process into single-output "allocated" processes, and inspect the resulting allocation factors.

Everything here uses the real installed multifunctional API (.venv/lib/python3.11/site-packages/multifunctional/, version 1.1.1), verified by running it. See the multifunctional module map for the full picture, and the empty-database tutorial for the plain bw2data basics this builds on.

1. Create a database with the multifunctional backend

A normal bd.Database(name) uses the default SQLite backend, which requires a square technosphere matrix — one product per process. Passing backend="multifunctional" routes the database through MultifunctionalDatabase (database.py in the installed package), which is registered into bw2data.subclass_mapping.DATABASE_BACKEND_MAPPING["multifunctional"] at import time (see the module map's first Q&A entry). We also set a database-wide default_allocation strategy here, since MaybeMultifunctionalProcess.allocate() falls back to it whenever a process doesn't name its own strategy: 

import bw2data as bd

bd.projects.set_current("mf_tutorial")

db = bd.Database("meat_and_leather", backend="multifunctional")
db.register(default_allocation="mass")

register(**kwargs) (bw2data/data_store.py DataStore.register()) stores whatever keyword arguments you pass into the database's metadata dict, which is exactly where MaybeMultifunctionalProcess.allocate() looks (node_classes.py line ~62: databases[self["database"]].get("default_allocation")).

2. Add ordinary, single-output supporting activities

Nothing about upstream/downstream activities needs to change — they're plain process nodes with a normal self-referencing production exchange, exactly like the empty-database tutorial: 

feed = db.new_activity(code="feed", name="cattle feed production", unit="kilogram", location="GLO", type="process")
feed.save()
feed.new_exchange(input=feed.key, amount=1, type="production").save()

3. Create separate product nodes for each co-product

A multifunctional process's functional exchanges should link to distinct product nodes, not to the process itself — that's what lets generic_allocation() (allocation.py lines 21-157) recover a real product name/unit for each split-off process. If a functional edge's input already resolves to a known node, generic_allocation() takes the "manual input product" branch (line ~89) and reads reference product/unit straight off it (line ~139); if you instead self-reference the multifunctional process (as a single-output activity would), it falls into the same branch but resolves the product to the *parent* process itself, which is not what you want for a genuine co-product: 

beef_product = db.new_node(code="beef", name="beef", unit="kilogram", location="GLO", type="product")
beef_product.save()
hide_product = db.new_node(code="hide", name="hide", unit="kilogram", location="GLO", type="product")
hide_product.save()

4. Create the multifunctional process with two functional exchanges

A node becomes multifunctional purely by having more than one exchange with functional=True — see BaseMultifunctionalNode.multifunctional (node_classes.py line ~26), which is len(list(self.functional_edges())) > 1. Each functional exchange also carries a properties dict with the numeric values the allocation strategies read (a mass value and a price value per co-product, here). Because the built-in "mass"/"price" strategies multiply the edge amount by the property (see step 6), and our exchange amounts are already in kilograms, we set mass=1.0 for both — the property represents "mass per unit of the exchange's own unit", not an independent total mass: 

cow = db.new_activity(code="cow_slaughter", name="cow slaughter", unit="cow", location="GLO", type="multifunctional")
cow.save()

cow.new_exchange(
    input=beef_product.key, amount=120, type="production", functional=True,
    name="beef", unit="kilogram", properties={"mass": 1.0, "price": 8.0},
).save()
cow.new_exchange(
    input=hide_product.key, amount=30, type="production", functional=True,
    name="hide", unit="kilogram", properties={"mass": 1.0, "price": 1.5},
).save()
cow.new_exchange(input=feed.key, amount=200, type="technosphere", name="cattle feed", unit="kilogram").save()

print(cow.multifunctional)                       # True
print([e["name"] for e in cow.functional_edges()])  # ['beef', 'hide']
True
['beef', 'hide']

Setting type="multifunctional" explicitly here is just for readability — in real usage you'd typically leave type unset and let MaybeMultifunctionalProcess.save() call utils.set_correct_process_type() to compute it for you from the exchange data every time you save.

5. Run allocation

MaybeMultifunctionalProcess.allocate() (node_classes.py lines ~46-79) is the entry point. With no strategy label given it resolves one from the process's own default_allocation, else the database's (the "mass" we set in step 1), looks it up in allocation_strategies, and calls it on self. That dispatches to generic_allocation() (allocation.py), which computes one allocation factor per functional edge, builds a full single-output process dict per co-product (functional edge kept + non-functional edges rescaled by the factor, rescale_exchange() from bw2io.utils), and hands the list to utils.update_datasets_from_allocation_results(), which writes them as real ReadOnlyProcessWithReferenceProduct nodes/edges in the database: 

cow.allocate()  # uses the database default_allocation = "mass"

for exc in cow.functional_edges():
    print(exc["name"], exc["mf_allocation_factor"])
beef 0.8
hide 0.2

0.8/0.2 is exactly the mass split (120 kg beef : 30 kg hide, out of 150 kg total). get_allocation_factor_from_property() (allocation.py lines 160-178) computes each edge's raw value as edge_data["amount"] * edge_data["properties"]["mass"] when normalize_by_production_amount=True (the default for "mass" and "price"), then generic_allocation() divides each by the sum over all functional edges — this is also why mass=1.0 above, not mass=120: setting it to the amount again would square the weighting.

6. Switch allocation strategy and compare

Allocation is not baked in — call .allocate(strategy_label=...) again with a different key from allocation_strategies ("price", "mass", "equal", "manual_allocation", or any strategy you've registered via custom_allocation.add_custom_property_allocation_to_project()) to re-derive the split and overwrite the previous allocated processes: 

cow.allocate(strategy_label="price")
for exc in cow.functional_edges():
    print("price:", exc["name"], exc["mf_allocation_factor"])

cow.allocate(strategy_label="equal")
for exc in cow.functional_edges():
    print("equal:", exc["name"], exc["mf_allocation_factor"])
price: beef 0.9552238805970149
price: hide 0.04477611940298507
equal: beef 0.5
equal: hide 0.5

Economic allocation by price (8.0 vs 1.5 $/kg) skews heavily toward beef (120×8.0 = 960 vs 30×1.5 = 45, so 960/1005 ≈ 0.955), while "equal" (allocation.py line 201, func=lambda x, y: 1.0) ignores properties entirely and gives every functional edge the same weight regardless of amount.

7. Inspect the resulting single-output processes

Each call to .allocate() re-runs generic_allocation(), which stamps a fresh mf_allocation_run_uuid on the parent (allocation.py line ~54) and regenerates the allocated processes; MaybeMultifunctionalProcess.save() / ReadOnlyProcessWithReferenceProduct.save() call utils.purge_expired_linked_readonly_processes() so stale processes from a previous strategy don't linger. After the "equal" run above, the database holds one read-only process per co-product, each with the functional edge kept at its original amount and every non-functional edge rescaled by that co-product's factor: 

for act in sorted(db, key=lambda a: a.get("reference product") or ""):
    if act.get("type") == "readonly_process":
        print(act.get("reference product"), "production amount=", act.get("production amount"))
        for e in act.technosphere():
            print("   technosphere:", e["name"], e["amount"])
beef production amount= 120
   technosphere: cattle feed 100.0
hide production amount= 30
   technosphere: cattle feed 100.0

(The database iterates nodes in whatever order SQLite returns them, so the example sorts by reference product for a stable, repeatable order — don't rely on unsorted iteration order yourself.) With "equal" allocation both processes take half of the 200 kg feed input (100 kg each) regardless of how much beef or hide they actually produce — a visible illustration of why the allocation strategy matters. Each of these ReadOnlyProcessWithReferenceProduct nodes (node_classes.py) is a normal, single-output process as far as bw2calc is concerned: it has exactly one functional (production) edge, so it slots into a square technosphere matrix. They're read-only — their __setitem__, copy(), and new_edge() all raise NotImplementedError — because they're generated data; edit the parent multifunctional process (reachable from a read-only process via its .parent property) and re-run .allocate() instead.

8. Processing a database allocates automatically

You don't normally need to call .allocate() by hand at all. MultifunctionalDatabase.process() (database.py lines ~59-66) calls node.allocate(...) on every multifunctional node in the database before building the bw_processing datapackage that bw2calc.LCA consumes — the same processing step that runs automatically after every write. So as long as a process's default_allocation (or its database's) is set, saving the database is enough to keep the allocated processes current: 

db.process()  # re-allocates every multifunctional node, then builds the datapackage
print("processed OK")
processed OK

Notes & gotchas

  • Link functional exchanges to real product nodes, not to the process itself. Self-referencing (the pattern a single-output activity uses) is legal but makes generic_allocation() resolve the "product" back to the parent process, so every allocated process ends up with the parent's name as its reference product instead of the actual co-product's name.
  • The "mass"/"price" built-ins multiply amount × property. get_allocation_factor_from_property() (allocation.py line ~172) does edge_data["amount"] * edge_data["properties"][property_label] by default (normalize_by_production_amount=True). If your property value is already a total (not a per-unit rate), use "manual_allocation" instead, which reads the property directly without multiplying by amount (line ~198), or pass normalize_by_production_amount=False to a custom property_allocation() strategy.
  • Every functional edge needs the property, or allocation raises KeyError. Validate first with multifunctional.check_property_for_allocation() / list_available_properties() (custom_allocation.py) rather than discovering a missing property mid-allocation.
  • Re-allocating replaces, it doesn't accumulate. Each .allocate() call stamps a new mf_allocation_run_uuid and purge_expired_linked_readonly_processes() deletes read-only processes left over from the previous run — you never end up with stale allocated processes from an old strategy sitting alongside new ones.
  • Read-only processes really are read-only. Trying to edit one directly (or its exchanges, wrapped in ReadOnlyExchange/ReadOnlyExchanges from edge_classes.py) raises NotImplementedError. Use readonly_process.parent to get back to the editable multifunctional process.
  • A process with only one functional edge is a no-op. MaybeMultifunctionalProcess.allocate() returns NoAllocationNeeded immediately (after saving) if self.multifunctional is False — allocation only does anything once a process has 2+ functional edges.
