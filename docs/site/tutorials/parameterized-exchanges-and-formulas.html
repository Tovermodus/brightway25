Tutorial: parameterized exchanges and formulas

Give an exchange's amount a formula instead of a fixed number — driven by named parameters at the project and activity scope — so that changing one number in one place updates every exchange (and every downstream LCA score) that depends on it.

Everything here uses the real installed bw2data/bw2parameters API, verified by running it. This builds directly on Your first LCA calculation — same steel/CO₂ model, with the fixed 1.8 emission factor replaced by a formula. See the bw2parameters module map for how formula evaluation and dependency ordering work underneath, and the bw2calc module map for how Monte Carlo sampling on exchange uncertainty (a different mechanism — see that tutorial) differs from this.

1. Why parameterize an exchange

Every exchange amount so far has been a literal number typed once. That's fine for a fixed model, but breaks down the moment two exchanges should always move together (e.g. "this process's fuel use and its CO₂ both scale with the same efficiency number") or a value should be easy to sweep across scenarios. A parameter is a named, reusable number; a formula is a Python expression string stored on an exchange (or activity) in place of a fixed amount, referencing one or more parameter names. bw2data.parameters (backed by bw2parameters' formula interpreter and dependency-ordering) resolves formulas into concrete amounts on demand.

2. Build the model, with a formula instead of a number

Same biosphere flow and process as before, but the CO₂ exchange's amount starts at 0 — a placeholder — and its real value comes from a formula string referencing two parameters that don't exist yet: 

import bw2data as bd

bd.projects.set_current("params-tutorial")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

db = bd.Database("example_db")
db.register()
steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()

co2_exchange = steel.new_exchange(
    input=co2.key, amount=0, type="biosphere", formula="co2_per_kg * ore_purity"
)
co2_exchange.save()

3. A project-level parameter

co2_per_kg is a project-wide constant, visible to every database/activity in the project — register it with bd.parameters.new_project_parameters(...) (an alias for the ParameterManager singleton, bw2data/parameters.py ParameterManager.new_project_parameters): 

bd.parameters.new_project_parameters([
    {"name": "co2_per_kg", "amount": 2.0},
])

4. An activity-level parameter

ore_purity instead belongs to this one activity. Activity parameters live in a named group (auto-created if it doesn't exist) — groups are how bw2data scopes which formulas can see which parameters, and are also the unit that gets recalculated together: 

group = "steel_group"
bd.parameters.new_activity_parameters([
    {"name": "ore_purity", "database": "example_db", "code": "steel", "amount": 0.9},
], group)

This alone does not yet connect the group to the CO₂ exchange's formula — that link is explicit, next.

5. Link the exchange to the group, then solve

add_exchanges_to_group(group, activity) scans the activity's exchanges for formula fields and registers each as a ParameterizedExchange tied to that group; recalculate() then walks every group, evaluates formulas in dependency order (project → database → activity, via bw2parameters.ParameterSet under the hood), and writes the resulting numbers back onto the real exchange rows: 

bd.parameters.add_exchanges_to_group(group, steel)
bd.parameters.recalculate()

co2_exchange = next(exc for exc in steel.exchanges() if exc["type"] == "biosphere")
print(co2_exchange["amount"])
1.8

2.0 × 0.9 = 1.8 — the formula was evaluated and the exchange's stored amount field was overwritten with the result. From here, bw2calc.LCA doesn't know or care that this number came from a formula; it just reads the exchange like any other: 

import bw2calc as bc

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])

lca = bc.LCA({steel.key: 1}, method_key)
lca.lci()
lca.lcia()
print(lca.score)
1.7999999523162842

6. Change the parameter, not the exchange

This is the entire point: update the named parameter and recalculate, and every exchange whose formula depends on it updates too — you never touch the exchange directly. Calling new_project_parameters again with the same name overwrites it (the default overwrite=True): 

bd.parameters.new_project_parameters([
    {"name": "co2_per_kg", "amount": 3.0},   # was 2.0
])
bd.parameters.recalculate()

co2_exchange = next(exc for exc in steel.exchanges() if exc["type"] == "biosphere")
print(co2_exchange["amount"])

lca2 = bc.LCA({steel.key: 1}, method_key)
lca2.lci()
lca2.lcia()
print(lca2.score)
2.7
2.700000047683716

One number changed, in one place; the exchange amount and the LCA score both followed it through without editing either directly.

Full example, start to finish

import bw2data as bd
import bw2calc as bc

bd.projects.set_current("params-tutorial")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

db = bd.Database("example_db")
db.register()
steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()
co2_exchange = steel.new_exchange(
    input=co2.key, amount=0, type="biosphere", formula="co2_per_kg * ore_purity"
)
co2_exchange.save()

bd.parameters.new_project_parameters([{"name": "co2_per_kg", "amount": 2.0}])
group = "steel_group"
bd.parameters.new_activity_parameters(
    [{"name": "ore_purity", "database": "example_db", "code": "steel", "amount": 0.9}], group
)
bd.parameters.add_exchanges_to_group(group, steel)
bd.parameters.recalculate()

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])

lca = bc.LCA({steel.key: 1}, method_key)
lca.lci()
lca.lcia()
print(lca.score)  # 1.7999999523162842

bd.parameters.new_project_parameters([{"name": "co2_per_kg", "amount": 3.0}])
bd.parameters.recalculate()

lca2 = bc.LCA({steel.key: 1}, method_key)
lca2.lci()
lca2.lcia()
print(lca2.score)  # 2.700000047683716

Notes & gotchas

  • Formulas are just Python expression strings, evaluated by bw2parameters.Interpreter (a restricted asteval interpreter — see the bw2parameters module map), not real Python eval(); only referenced parameter names and a safe function/operator subset are available.
  • Three scopes, resolved together: project → database → activity. This tutorial only uses project and activity scope; new_database_parameters(data, database) sits in between for a value shared by every activity in one database but not the whole project.
  • Groups are the unit of recalculation and linkage. An activity parameter always belongs to a group; add_exchanges_to_group is what actually makes an exchange's formula field participate in recalculation — defining the parameter alone isn't enough if no exchange (or activity amount) references it via a linked group.
  • Recalculation is not automatic. Editing a parameter's amount does nothing to stored exchange amounts until bd.parameters.recalculate() (or the more targeted ActivityParameter.recalculate_exchanges(group)) runs — and until then, bw2calc.LCA still sees the old, stale amount, since it reads the exchange row, not the formula.
  • This is a different Monte Carlo path than exchange uncertainty. bw2parameters.ParameterSet.evaluate_monte_carlo() samples uncertainty on named parameters; bw2calc.LCA(..., use_distributions=True) (see Run a Monte Carlo uncertainty analysis) samples uncertainty directly on exchanges instead — formulas and exchange-level uncertainty distributions are two independent mechanisms that happen to share the same stats_arrays distribution classes underneath.
  • An unresolved or circular formula fails loudly. A formula referencing an undefined name raises bw2parameters.errors.MissingName (often surfaced as bw2data.parameters' own MissingName/ParameterError) at recalculate() time, not when the formula string was first saved — a saved-but-unlinked or misspelled formula stays silently un-evaluated until the group it belongs to is recalculated.
