Tutorial: search and browse a database

Every other tutorial looks an activity up by exact name with db.get(name=...). That only works once you already know the exact name. This walks through bw2data's actual full-text search, plus the plain-Python ways to filter and browse when you don't.

Everything here uses the real installed bw2data API (.venv/lib/python3.11/site-packages/bw2data/), verified by running it — including one place where the installed behavior has quietly diverged from what its own docstring still says. Continues from Import and run an LCA on an external database, reusing the "Mobility example" dataset it imports.

1. Get a database to browse

A hand-typed toy database with two activities has nothing worth searching. Import the bundled "Mobility example" dataset the same way as the external-database tutorial — 9 activities across cars, batteries, electricity, and driving: 

import bw2data as bd
import bw2io as bi

bd.projects.set_current("search-tutorial")
bi.add_example_database()

db = bd.Database("Mobility example")
print(len(db), "activities")
9 activities

2. Full-text search with db.search()

SQLiteBackend.search(string, **kwargs) (bw2data/backends/base.py:1113) searches a per-database SQLite FTS5 index over the name, comment, product, categories, synonyms, and location fields (bw2data/search/search.py Searcher), weighted by relevance (name counts 5× more than comment by default). It's built automatically: write() calls make_searchable() whenever searchable=True (the default), which indexes every activity via IndexManager.add_datasets(). 

results = db.search("car")
for act in sorted(results, key=lambda a: a["name"]):
    print(act["name"])
Combustion car
Driving an combustion car
Driving an electric car
Electric car
Electric car battery

Results come back as ordinary Activity proxies (pass proxy=False to get raw index rows instead), nominally ranked most-relevant-first — in practice, ties in relevance (all 5 results above match only on name, so their raw scores tie) come back in a different order on different runs of the same query, so anything downstream that needs a stable order should still sort explicitly, as done here. Wildcards work with a trailing *: 

print(sorted(act["name"] for act in db.search("elect*")))
['Driving an electric car', 'Electric car', 'Electric car battery', 'Electricity']

3. filter=/mask= look supported — they aren't, in this version

SQLiteBackend.search()'s own docstring still documents filter and mask keyword arguments ("Dictionary of criteria that search results must meet/exclude"). Reading the actually-installed implementation (bw2data/search/indices.py IndexManager.search(), around line 110) tells a different story: both arguments now just emit a DeprecationWarning and do nothing. This is exactly the kind of drift the root CLAUDE.md warns about — a docstring/upstream description that no longer matches installed behavior: 

results = db.search("car", filter={"location": "Europe"})
print(sorted(act["name"] for act in results))  # filter is silently ignored!
['Combustion car', 'Driving an combustion car', 'Driving an electric car', 'Electric car', 'Electric car battery']

All 5 "car" results came back, including the GLO-located ones — filter did not narrow anything. The fix is to filter in plain Python after the search returns, which always works and doesn't depend on index internals: 

results = [act for act in db.search("car") if act.get("location") == "Europe"]
print(sorted(act["name"] for act in results))
['Driving an combustion car', 'Driving an electric car']

4. Browsing without search: plain iteration

For anything that isn't fuzzy text matching — "every activity with this unit", "every activity in this location" — just iterate the database and filter with a list comprehension. A bw2data.Database is directly iterable (SQLiteBackend.__iter__) and each activity behaves like a dict for its metadata fields: 

kilogram_activities = [act for act in db if act.get("unit") == "kilogram"]
print(sorted(act["name"] for act in kilogram_activities))
['CO2', 'Lithium', 'Steel']

This is a plain Python loop over however many activities the database has — fine for hundreds or low thousands of activities, but it's a full table scan; db.search()'s SQL index is the better tool once a database is ecoinvent-sized (tens of thousands of activities).

5. Exact lookup once you know what you want

Once search or filtering has narrowed things down to one activity, switch to Database.get(**filters) (exact-match keyword filters, raises if zero or more than one match) or module-level bw2data.get_node(**filters) (searches across all databases in the project, not just one): 

steel = db.get(name="Steel")
print(steel, steel["location"])

same = bd.get_node(database="Mobility example", name="Steel")
print(steel.id == same.id)
'Steel' (kilogram, GLO, None) GLO
True

Full example, start to finish

import bw2data as bd
import bw2io as bi

bd.projects.set_current("search-tutorial")
bi.add_example_database()

db = bd.Database("Mobility example")

# full-text search (sort explicitly -- ties in relevance aren't stably ordered)
print(sorted(act["name"] for act in db.search("car")))

# filter= is a documented-but-dead no-op in this installed version -- filter
# the returned list in plain Python instead
european = [act for act in db.search("car") if act.get("location") == "Europe"]
print(sorted(act["name"] for act in european))

# plain iteration + comprehension for non-text filters
print(sorted(act["name"] for act in db if act.get("unit") == "kilogram"))

# exact lookup once you know the name
steel = db.get(name="Steel")
print(steel)

Notes & gotchas

  • filter/mask do nothing in this installed version (verified above) — don't rely on their docstring description; filter the returned list yourself.
  • Search only covers a fixed field set (name, comment, product, categories, synonyms, location) — searching on e.g. unit or a custom field will never match; use plain iteration for those instead.
  • A database must be searchable to use .search(). It's the default (write(..., searchable=True)), but db.register()'s write_empty=True path writes with searchable=False — call db.make_searchable() once you've added real content if you registered an empty database first (see Create an empty database).
  • facet= is unreliable in this installed version. db.search("*", facet="location") is meant to return a dict of {location: [activities]}, but Searcher.search() (bw2data/search/search.py) builds it with itertools.groupby(results, lambda x: x.get(facet)) — groupby only merges consecutive equal keys, and search results aren't sorted by the facet field, so activities sharing a location silently get split into separate groups that overwrite each other in the dict comprehension (verified: re-running the same query returns a different, sometimes-incomplete set of names per location each time). Don't rely on it; group the plain result list yourself with sorted(results, key=lambda a: a[facet]) + itertools.groupby (now correctly consecutive), or a plain dict/defaultdict loop.
  • bw2data.query.Query/Filter is a separate, older in-memory filter DSL over plain Python dicts/lists (not the SQL-backed search index) — useful if you already have a list of dataset dicts (e.g. mid-import, before write_database()) rather than a written, queryable database.
