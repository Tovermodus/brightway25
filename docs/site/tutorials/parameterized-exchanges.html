Tutorial: use formulas in exchanges (parameterized activities)

Define a project parameter, have an activity parameter and an exchange's amount both derive from it via a formula field, recalculate, and watch the numbers cascade when the parameter changes.

Everything here uses the real installed bw2data.parameters API (.venv/lib/python3.11/site-packages/bw2data/parameters.py), which hands formula evaluation off to bw2parameters. Every snippet below, including the full example, was actually run against the installed source — see the bw2data module map for how this fits into the rest of Brightway.

1. Set up an activity with a parameterizable exchange

This is the same project/database/activity setup as the empty-database tutorial: a project, a database, a steel production activity with a production exchange, and an iron ore product it consumes as a technosphere input. 

import bw2data as bd

bd.projects.set_current("param_tutorial")
db = bd.Database("example_db")
db.register()

iron_ore = db.new_node(code="raw_ore", name="iron ore", unit="kilogram", location="GLO", type="product")
iron_ore.save()

steel = db.new_activity(code="steel_production", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()

2. Give an exchange a formula instead of a fixed amount

Any exchange dict can carry a formula field (a Python expression string) alongside its numeric amount — Exchange (bw2data/backends/proxies.py) is a plain MutableMapping proxy over the row, so this is nothing more than an extra key: 

exc = steel.new_exchange(input=iron_ore.key, amount=1, type="technosphere", formula="scale * 1.5")
exc.save()

print(exc["amount"], exc["formula"])
1 scale * 1.5

Note the amount is still 1 — saving a formula field does not evaluate it. Exchange.save() just writes the row; nothing in bw2data looks at formula strings until you explicitly register this activity's parameters and exchanges with the ParameterManager and recalculate, which is what the rest of this tutorial does.

3. Define a project-level parameter

Project parameters are the outermost scope — plain named values (or formulas of their own) visible to every database/activity parameter in the project. Create them with bd.parameters.new_project_parameters() (ParameterManager.new_project_parameters, parameters.py:1326), which upserts a list of {"name", "amount", "formula", ...} dicts into the ProjectParameter table and immediately recalculates the "project" group: 

bd.parameters.new_project_parameters([{"name": "ore_price", "amount": 2.5}])

4. Define an activity parameter that depends on it

Activity parameters live in a named group (usually one group per activity, but a group can span several activities) and can reference project — and other activity — parameters by name in their own formula. Create them with bd.parameters.new_activity_parameters(data, group) (parameters.py:1440): 

from bw2data.parameters import ActivityParameter

bd.parameters.new_activity_parameters(
    [{"name": "scale", "database": "example_db", "code": "steel_production", "formula": "ore_price * 2"}],
    "steel_group",
)
print(ActivityParameter.get(group="steel_group", name="scale").amount)
5.0

new_activity_parameters already evaluates scale for you (2.5 * 2 = 5.0) — it ends by calling ActivityParameter.recalculate(group) (parameters.py:1509), which resolves the dependency chain (ActivityParameter.dependency_chain()), recalculates any expired upstream project/database parameters first, then evaluates this group's own parameters with a bw2parameters.ParameterSet (ParameterSet(data, static).evaluate_and_set_amount_field(), parameters.py:843) — the same topological-sort-then-evaluate engine documented on the bw2parameters page.

5. Link the exchange's formula into the group, then recalculate

An exchange's formula field is inert until it's registered as a ParameterizedExchange row in the same group as the activity parameters it references. Do that with bd.parameters.add_exchanges_to_group(group, activity) (parameters.py:1271), which scans activity.exchanges() for any exchange carrying a formula key and creates/updates a matching ParameterizedExchange; then call bd.parameters.recalculate() (parameters.py:1610) to actually run the formulas: 

bd.parameters.add_exchanges_to_group("steel_group", steel)
bd.parameters.recalculate()

exc = next(e for e in steel.exchanges() if e["input"] == iron_ore.key)
print(exc["amount"])
7.5

scale is 5.0 and the exchange's formula is "scale * 1.5", so 5.0 * 1.5 = 7.5 — and that's now what's stored as the exchange's amount on disk.

6. Change the parameter and watch the exchange amount follow

Calling new_project_parameters() again with the same name overwrites it (the default overwrite=True) and marks the "project" group's downstream dependents expired via ProjectParameter.expire_downstream("project") (parameters.py:201). A subsequent bd.parameters.recalculate() walks every non-fresh Group (parameters.py:1617) and re-evaluates it — project parameter, then dependent activity parameter, then dependent exchange, in that order: 

bd.parameters.new_project_parameters([{"name": "ore_price", "amount": 10}])
bd.parameters.recalculate()

exc = next(e for e in steel.exchanges() if e["input"] == iron_ore.key)
print("scale =", ActivityParameter.get(group="steel_group", name="scale").amount)
print("exchange amount =", exc["amount"])
scale = 20.0
exchange amount = 30.0

ore_price going from 2.5 to 10 re-derives scale = 10 * 2 = 20.0, which re-derives the exchange amount 20.0 * 1.5 = 30.0 — one parameter change, cascaded through two formulas, with no manual recomputation of either downstream value.

Full example, start to finish

import bw2data as bd
from bw2data.parameters import ActivityParameter

bd.projects.set_current("param_tutorial")

db = bd.Database("example_db")
db.register()

iron_ore = db.new_node(code="raw_ore", name="iron ore", unit="kilogram", location="GLO", type="product")
iron_ore.save()

steel = db.new_activity(code="steel_production", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()
steel.new_exchange(input=iron_ore.key, amount=1, type="technosphere", formula="scale * 1.5").save()

bd.parameters.new_project_parameters([{"name": "ore_price", "amount": 2.5}])
bd.parameters.new_activity_parameters(
    [{"name": "scale", "database": "example_db", "code": "steel_production", "formula": "ore_price * 2"}],
    "steel_group",
)
bd.parameters.add_exchanges_to_group("steel_group", steel)
bd.parameters.recalculate()

exc = next(e for e in steel.exchanges() if e["input"] == iron_ore.key)
print("ore_price = 2.5  ->  scale =", ActivityParameter.get(group="steel_group", name="scale").amount,
      " exchange amount =", exc["amount"])

bd.parameters.new_project_parameters([{"name": "ore_price", "amount": 10}])
bd.parameters.recalculate()

exc = next(e for e in steel.exchanges() if e["input"] == iron_ore.key)
print("ore_price = 10   ->  scale =", ActivityParameter.get(group="steel_group", name="scale").amount,
      " exchange amount =", exc["amount"])
ore_price = 2.5  ->  scale = 5.0  exchange amount = 7.5
ore_price = 10   ->  scale = 20.0  exchange amount = 30.0

Notes & gotchas

  • A formula field alone does nothing. It's just a string stored on the exchange row until you (a) register the activity's parameters via new_activity_parameters/add_to_group, (b) link its formula-carrying exchanges into that same group with add_exchanges_to_group, and (c) call recalculate(). Skipping step (b) is the easiest mistake — the exchange keeps its stale amount forever, silently.
  • Two different formula evaluators are involved, at two different layers. Activity/project/database parameter values are evaluated together as an interdependent set via bw2parameters.ParameterSet (topologically sorted so a parameter can reference another parameter in any order, parameters.py:843). Exchange formulas, by contrast, are evaluated one at a time with a plain asteval.Interpreter — not bw2parameters.Interpreter — seeded with the group's already-resolved parameter values (ActivityParameter.recalculate_exchanges(), parameters.py:861-873). Practically this means an exchange formula can reference any parameter in its group, but not another exchange.
  • Groups, not activities, are the unit of recalculation. Group (parameters.py:1109) tracks a fresh flag; any parameter or ParameterizedExchange save expires its group (ActivityParameter.save(), ParameterizedExchange.save(), parameters.py:882-883 and :1087), and ParameterManager.recalculate() (parameters.py:1610) only touches groups that are actually stale — calling it repeatedly is cheap once everything is fresh.
  • Dependencies cascade automatically, in order. ActivityParameter.recalculate(group) walks ActivityParameter.dependency_chain(group) and recalculates upstream project/database groups first (parameters.py:823-836) before this group's own parameters, then finishes by calling recalculate_exchanges() for this group (parameters.py:855) — that's the whole chain behind step 6 above updating both scale and the exchange amount from one project-parameter edit.
  • The exchange amount really is overwritten, not just displayed. recalculate_exchanges() sets exc.data["amount"] directly on the underlying ExchangeDataset row and saves it (parameters.py:872-873) — the original amount you passed to new_exchange() is gone unless you'd captured it. add_exchanges_to_group() stashes it as original_amount the first time (parameters.py:1300-1302), and remove_exchanges_from_group(..., restore_original=True) (the default) restores it if you later pull the activity out of parameterization.
  • A skipped step: real usage often defines activity parameters via activity["parameters"] = [...]; bd.parameters.add_to_group(group, activity) instead of calling new_activity_parameters directly — add_to_group (parameters.py:1175) reads that list off the activity dict, creates the ActivityParameter rows, then calls add_exchanges_to_group itself, folding steps 4 and 5 above into one call. This tutorial keeps them separate to show what each one actually does.
