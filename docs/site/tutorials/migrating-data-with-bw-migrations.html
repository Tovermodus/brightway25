Tutorial: relink flow names/units with bw_migrations

How to load a curated migration table and apply it to plain data dicts — the naming/unit-reconciliation step that runs before data ever touches bw2data, and the building block underneath hybrid/IO-based LCA import pipelines.

Everything here uses the real installed bw_migrations API (.venv/lib/python3.11/site-packages/bw_migrations/), verified by running it. See the bw_migrations module map for the full picture, and the bw2io module map for how import pipelines actually invoke migrations like this one.

1. What a "migration" is here

In this package, a migration is nothing more than a lookup table: a list of [key_tuple, replacement] pairs, where key_tuple is built from one or more fields of a data dict (e.g. (name, categories)) and replacement is a dict of fields to overwrite (name, unit, categories, ...), optionally carrying a __multiplier__ / __disaggregation__ rescale factor. Applying a migration means: for every row in a dataset, look up its key tuple, and if there's a match, overwrite (and possibly rescale) that row in place.

This is exactly the kind of linking step hybrid/input-output LCA needs: process-based inventory data (ecoinvent-style activities and biosphere flows) and IO/MRIO background data (EXIOBASE-style sectors and environmental extensions) are built by different teams with different naming conventions, units, and flow granularity. Before the two can be combined into one system, the flow names on one side have to be rewritten to match the other. bw_migrations ships exactly one bundled migration for this — EXIOBASE 3 biosphere flows → ecoinvent 3.6 biosphere flows — and bw2io's EXIOBASE import strategies use it (and packages like it) as a building block before writing anything into a bw2data database.

2. Load the bundled migration

get_migration(location) resolves a migration by bundled name, file path, or in-memory Mapping. The bundled EXIOBASE→ecoinvent migration is a plain dict with fields/data (plus provenance metadata): 

from bw_migrations import get_migration

migration = get_migration("exiobase-3-ecoinvent-3.6")
print(sorted(migration.keys()))
print("fields:", migration["fields"])
print("number of mapped flows:", len(migration["data"]))
print("license:", migration["license"]["name"])
['contributors', 'data', 'fields', 'license', 'missing flows', 'version']
fields: ['name', 'categories']
number of mapped flows: 82
license: ODC-PDDL-1.0

Each entry in data is a [key, replacement] pair. The key is matched against a row's (name, categories) values; the replacement is either a single dict (rename/rescale in place) or a list of dicts (split one source flow into several target flows). Two real entries, straight out of the bundled file: 

for row in migration["data"][:2]:
    print(row)
[['1,3 Butadiene', 'air'], {'unit': 'kilogram', '__multiplier__': 1000, 'name': 'Butadiene'}]
[['As', 'air'], {'unit': 'kilogram', '__multiplier__': 1000, 'name': 'Arsenic'}]

Reading this: an EXIOBASE flow named "1,3 Butadiene" in compartment "air" becomes ecoinvent's "Butadiene", with its amount rescaled ×1000 and its unit set to "kilogram" (EXIOBASE reports these flows in tonnes; ecoinvent uses kilograms).

3. Apply it to a small dataset

migrate_data(data, migration) is a generator: it builds a lookup dict keyed by tuple(row[field] for field in migration["fields"]), then for each row either yields it unchanged (no match) or applies the replacement via modify_object(). Build three EXIOBASE-style rows — two whose (name, categories) really are keys in the bundled migration (confirmed above), one that isn't: 

import copy
from bw_migrations import migrate_data

flows = [
    {"name": "1,3 Butadiene", "categories": "air", "amount": 0.002, "unit": "kg", "type": "biosphere"},
    {"name": "As", "categories": "air", "amount": 0.0005, "unit": "kg", "type": "biosphere"},
    {"name": "some unmapped flow", "categories": "soil", "amount": 1.0, "unit": "kg", "type": "biosphere"},
]
originals = copy.deepcopy(flows)   # migrate_data modifies matched rows in place

result = list(migrate_data(flows, migration))
for before, after in zip(originals, result):
    print("BEFORE:", before)
    print("AFTER: ", after)
    print()
BEFORE: {'name': '1,3 Butadiene', 'categories': 'air', 'amount': 0.002, 'unit': 'kg', 'type': 'biosphere'}
AFTER:  {'name': 'Butadiene', 'categories': 'air', 'amount': 2.0, 'unit': 'kilogram', 'type': 'biosphere'}

BEFORE: {'name': 'As', 'categories': 'air', 'amount': 0.0005, 'unit': 'kg', 'type': 'biosphere'}
AFTER:  {'name': 'Arsenic', 'categories': 'air', 'amount': 0.5, 'unit': 'kilogram', 'type': 'biosphere'}

BEFORE: {'name': 'some unmapped flow', 'categories': 'soil', 'amount': 1.0, 'unit': 'kg', 'type': 'biosphere'}
AFTER:  {'name': 'some unmapped flow', 'categories': 'soil', 'amount': 1.0, 'unit': 'kg', 'type': 'biosphere'}

The first two rows get renamed and rescaled (0.002 kg × 1000 = 2.0, now reported in "kilogram" to match the new name's convention) — matching a key touches every field in the replacement dict at once, not just the one you searched by. The third row has no entry for ("some unmapped flow", "soil") in the lookup, so migrate_data catches the resulting KeyError internally and yields the row completely unchanged. This is the important safety property: a migration is a best-effort relinking pass, not a filter — rows with nothing to say are passed through rather than dropped or raising.

4. Rescaling and fan-out (one source flow → several target flows)

The bundled migration also has entries whose replacement is a list of dicts, each carrying its own __multiplier__ and __disaggregation__ — this is how one aggregate EXIOBASE flow (e.g. "CFCs", lumping several individual chlorofluorocarbons together) gets split into several disaggregated ecoinvent flows, each taking a fraction of the original amount: 

flows = [{"name": "CFCs", "categories": "air", "amount": 0.006, "unit": "kg", "type": "biosphere"}]
originals = copy.deepcopy(flows)

result = list(migrate_data(flows, migration))
print("BEFORE:", originals[0])
print(f"AFTER: fanned out into {len(result)} rows")
for row in result:
    print(" ", row["name"], row["amount"], row["unit"])
BEFORE: {'name': 'CFCs', 'categories': 'air', 'amount': 0.006, 'unit': 'kg', 'type': 'biosphere'}
AFTER: fanned out into 6 rows
  Ethane, 1,1,2-trichloro-1,2,2-trifluoro-, CFC-113 1.0 kilogram
  Ethane, 1,2-dichloro-1,1,2,2-tetrafluoro-, CFC-114 1.0 kilogram
  Ethane, chloropentafluoro-, CFC-115 1.0 kilogram
  Methane, chlorotrifluoro-, CFC-13 1.0 kilogram
  Methane, dichlorodifluoro-, CFC-12 1.0 kilogram
  Methane, trichlorofluoro-, CFC-11 1.0 kilogram

The math behind that 1.0: each of the 6 replacement dicts carries __multiplier__=1000 and __disaggregation__=1/6 (0.16666...). strategies.modify_object() multiplies the two together into one scale factor and hands it to utils.rescale_object(), which applies it to amount (as well as formula and any stats_arrays-style uncertainty parameters, if present) — 0.006 × 1000 × (1/6) = 1.0 for every one of the six rows. A single input row becomes six output rows because the matched replacement was a list: migrate_data deep-copies the row once per replacement dict in the list and applies each one separately.

5. A custom migration (not the bundled one)

Nothing about migrate_data is specific to the EXIOBASE↔ecoinvent dataset — it's a generic find/replace-plus-rescale engine for any two datasets' naming conventions. Here's a minimal hand-built migration reconciling a hypothetical dataset that reports mass in tonnes with one that expects kilograms, matched by (name, unit): 

custom_migration = {
    "fields": ["name", "unit"],
    "data": [
        [["steel", "t"], {"unit": "kg", "__multiplier__": 1000}],
        [["concrete", "t"], {"unit": "kg", "__multiplier__": 1000}],
    ],
}

rows = [
    {"name": "steel", "unit": "t", "amount": 2.5},
    {"name": "concrete", "unit": "t", "amount": 10},
    {"name": "water", "unit": "m3", "amount": 5},
]
originals = copy.deepcopy(rows)

result = list(migrate_data(rows, custom_migration))
for before, after in zip(originals, result):
    print("BEFORE:", before)
    print("AFTER: ", after)
    print()
BEFORE: {'name': 'steel', 'unit': 't', 'amount': 2.5}
AFTER:  {'name': 'steel', 'unit': 'kg', 'amount': 2500.0}

BEFORE: {'name': 'concrete', 'unit': 't', 'amount': 10}
AFTER:  {'name': 'concrete', 'unit': 'kg', 'amount': 10000}

BEFORE: {'name': 'water', 'unit': 'm3', 'amount': 5}
AFTER:  {'name': 'water', 'unit': 'm3', 'amount': 5}

Same engine, same pass-through-on-no-match behavior (the water row, in m3 rather than t, doesn't match either key and is left alone) — only the migration dict changed. get_migration() would also happily load this same dict from a JSON file on disk if you saved it there, via a file path instead of a bundled name.

6. Where this fits

Everything above ran on plain Python dicts in a list — no bw2data project, no database, no import pipeline. That's the point: bw_migrations operates purely on in-memory data structures, before anything is written into a Brightway project. An import pipeline (like bw2io's EXIOBASE strategies) calls get_migration() and migrate_data() (or an equivalent renaming/rescaling strategy) as one step in a longer chain, so that by the time data reaches bw2data.Database.write() the flow names, units and categories already match the target database's conventions. See the bw2io module map for how strategies and its own, differently-named bw2io.migrations.Migration mechanism fit into a real import — they're a related but distinct mechanism (on-disk-registered, per-project, plain "multiplier" rescale key) from the standalone functions used here.
