Tutorial: your first LCA calculation

Start from a completely empty project and build up, piece by piece, the four things every Brightway LCA needs — a biosphere flow, a process that emits it, a characterization method, and a bw2calc.LCA object — explaining what each call does and why it's needed before running the numbers.

Everything here uses the real installed bw2data/bw2calc API, verified by running it. This is the slow-paced version of example 3 on the Examples page — read this first if example 3's 20 lines go by too fast, or if you haven't built an LCA from scratch before. Once this clicks, Create an empty database and Find an LCA result's biggest contributors pick up where this leaves off.

1. Why an LCA needs four pieces

An LCA score answers "how much impact does producing this much of this thing have, measured this way?" That sentence names everything you need:

  • a process that produces something and consumes/emits other things (an activity, with exchanges),
  • the things it emits into the environment (biosphere flows),
  • a method that says how much each biosphere flow matters (a characterization factor per flow), and
  • a functional unit — "this much of this thing" — handed to bw2calc.LCA, which does the matrix algebra and reports a single score.

All of Brightway's data (activities, exchanges, methods) lives inside a project (bw2data/project.py ProjectManager), so that's step zero.

2. Pick a project

import bw2data as bd

bd.projects.set_current("first-lca-tutorial")  # created automatically if new
print(bd.projects.current)
first-lca-tutorial

Everything you do below — every database, activity, and method — is scoped to whichever project is current. Switching projects with set_current again switches your entire visible dataset.

3. Register a biosphere flow

A biosphere flow is just another node, stored like any activity but with type="emission" (or another biosphere type — see bw2data.labels) and no exchanges of its own. It lives in its own database by convention (real projects call this database "biosphere3" and get it pre-filled by bw2io.bw2setup(); here we build one flow by hand so nothing outside this tutorial needs to exist yet): 

biosphere = bd.Database("biosphere")
biosphere.register()

co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()
print(co2)
'carbon dioxide' (kilogram, GLO, None)

This node is nothing more than a labeled bucket — "carbon dioxide, measured in kilograms" — that processes will point exchanges at, and that a method will later attach a weight to.

4. Build a process that emits it

A process is an activity in its own database, given meaning by its exchanges — most importantly a production exchange pointing at itself ("1 unit of this activity produces 1 kilogram of steel") and a biosphere exchange for each flow it emits: 

db = bd.Database("example_db")
db.register()

steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()

steel.new_exchange(input=steel.key, amount=1, type="production").save()
steel.new_exchange(input=co2.key, amount=1.8, type="biosphere").save()  # 1.8 kg CO2 per kg steel

print(steel, "with", len(list(steel.exchanges())), "exchanges")
'steel production' (kilogram, GLO, None) with 2 exchanges

Nothing about new_exchange knows or cares whether its input is a process or a biosphere flow — the exchange's own type field is what tells bw2calc which matrix (technosphere vs biosphere) it belongs in.

5. Register a characterization method

A Method is a lookup table from biosphere flow → a single number (its characterization factor, "how much does 1 kg of this flow count for"). Here we make a one-flow toy "global warming potential" method where CO₂ itself is the reference unit, so its factor is exactly 1.0: 

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])   # list of (flow key, characterization factor) pairs

print(bd.methods[method_key])
{'unit': 'kg CO2-eq', 'abbreviation': 'tutorial_methodg.e6e7620d8bfb141d5deb5b4ec3a27ed4', 'num_cfs': 1, 'geocollections': ['world']}

A real method (e.g. IPCC 2021 GWP100, shipped as part of bw2io.create_default_lcia_methods()) is exactly this same shape — a method key plus a list of (flow key, factor) pairs — just with hundreds of flows instead of one.

6. Run the LCA

bw2calc.LCA takes a functional unit — a dict {activity_key_or_id: amount} — and a method key. Building the score is two explicit steps: .lci() solves the technosphere system for how much of each biosphere flow the functional unit requires, and .lcia() multiplies that by the method's characterization factors: 

import bw2calc as bc

lca = bc.LCA({steel.key: 1}, method_key)  # functional unit: 1 kg of steel production
lca.lci()                                 # solve the inventory (how much CO2 is emitted)
lca.lcia()                                # apply the method's characterization factors
print(lca.score)
1.7999999523162842

1 kg of steel needed 1.8 kg of CO₂ (from the exchange above), and this method counts each kg of CO₂ as 1.0 kg CO2-eq, so the score is 1.8 — bw2calc stores it as a float32, hence the trailing digits.

7. Change the functional unit, not the model

The model you built (the activity, its exchanges, the method) doesn't change when you ask a different question — only the functional unit dict passed to LCA does. Producing 5 kg of steel instead of 1 kg scales the whole result linearly, because everything here is a linear technosphere: 

lca2 = bc.LCA({steel.key: 5}, method_key)
lca2.lci()
lca2.lcia()
print(lca2.score)
8.999999761581421

Full example, start to finish

import bw2data as bd
import bw2calc as bc

bd.projects.set_current("first-lca-tutorial")

biosphere = bd.Database("biosphere")
biosphere.register()
co2 = biosphere.new_node(code="co2", name="carbon dioxide", unit="kilogram", type="emission")
co2.save()

db = bd.Database("example_db")
db.register()
steel = db.new_node(code="steel", name="steel production", unit="kilogram", location="GLO")
steel.save()
steel.new_exchange(input=steel.key, amount=1, type="production").save()
steel.new_exchange(input=co2.key, amount=1.8, type="biosphere").save()

method_key = ("tutorial_method", "gwp")
method = bd.Method(method_key)
method.register(unit="kg CO2-eq")
method.write([(co2.key, 1.0)])

lca = bc.LCA({steel.key: 1}, method_key)
lca.lci()
lca.lcia()
print(lca.score)  # 1.7999999523162842

Notes & gotchas

  • Order doesn't matter much, existence does. You can register the method before or after the process — bw2calc.LCA only needs everything to exist and be .save()d/.write()ed by the time you call .lci().
  • A production exchange is not optional. Without steel.new_exchange(input=steel.key, amount=1, type="production"), bw2calc has no way to relate "1 unit of this activity" to anything — see the technosphere-matrix diagonal explanation on the bw2calc module map.
  • Functional units use whatever key LCA was given. Plain LCA accepts (database, code) tuples, Node/Activity objects, or integer ids as dict keys; bw2calc.MultiLCA (see example 6) is stricter and requires integer ids.
  • This is a toy method. A real GWP method (e.g. IPCC 2021) is registered the same way but with hundreds of characterization factors, normally imported wholesale via bw2io.create_default_lcia_methods() rather than typed by hand.
  • Next steps. To keep building this exact activity into a small multi-process system and rank its biggest contributors, continue with Find an LCA result's biggest contributors. To import a real external dataset instead of typing exchanges by hand, see Import and run an LCA on an external database.
